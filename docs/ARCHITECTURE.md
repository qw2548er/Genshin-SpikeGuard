# 架构设计文档

## 概述

Genshin SpikeGuard 采用**解势化架构**（Decoupled Architecture），各模块之间通过消息队列异步通信，完全解耦。这种设计的核心优势是：

1. **故障隔离** — 单个模块异常不会影响其他模块
2. **独立演进** — 模块可以独立修改、替换、升级
3. **可测试性** — 每个模块可以单独测试
4. **进程隔离** — 守护服务运行在独立进程

## 模块详细设计

### 1. 采集模块 (Collector)

**职责**：只采集，不决策

- 定时采样 GPU 负载、CPU 负载、帧率、温度、内存
- 通过性能数据估算实体数量
- 检测 GPU 尖峰和实体激增
- 将采样数据通过消息总线发布

**核心类**：
- `BaseCollector` — 采集器基类
- `GpuFrameCollector` — GPU与帧率采集器

**设计原则**：
- 采样频率可配置（默认 500ms）
- 异常时自动降级，不影响其他模块
- 只发布原始数据，不做判断

### 2. 决策模块 (Decision)

**职责**：只决策，不执行

- 场景识别：根据性能特征匹配预设场景
- 风险评估：评估当前风险等级
- 保护决策：决定是否触发保护、保护强度
- 风险缓释：控制保护频率，降低账号风险

**核心类**：
- `DecisionEngine` — 决策引擎

**决策流程**：
```
性能数据 → 尖峰检测 → 场景识别 → 风险预算检查 → 触发保护
                    ↓
                通用保护（未匹配场景）
```

**场景识别算法**：
- 基于多因素评分：实体估算值、连续尖峰数、帧率、GPU负载
- 评分 >= 60 分触发场景保护
- 最高评分场景胜出

**风险缓释策略**：
- 每小时保护次数上限
- 每日保护次数上限
- 最小保护间隔
- 渐进式强度升级
- 超过上限后冷却期

### 3. 执行模块 (Executor)

**职责**：只执行，不决策

- 根据决策结果执行保护动作
- 支持多种权限模式（Root / Shizuku / LogOnly）
- 渐变恢复，减少体感影响
- 退出时恢复所有系统设置

**核心类**：
- `ActionExecutor` — 执行器接口
- `RootActionExecutor` — Root 模式执行器
- `ShizukuActionExecutor` — Shizuku 模式执行器
- `LogOnlyExecutor` — 仅日志模式执行器
- `ExecutionManager` — 执行管理器

**保护动作**：
| 动作 | 说明 |
|------|------|
| CPU_THROTTLE | CPU 降频 |
| GPU_THROTTLE | GPU 降频 |
| FRAME_LIMIT | 帧率限制 |
| THERMAL_LIMIT | 温控调节 |

**渐变恢复**：
- 保护结束后，频率在 fade_out_ms 时间内线性恢复
- 减少频率突变带来的体感波动

### 4. UI 模块 (UI)

**职责**：用户交互和状态展示

- 实时性能数据展示
- 保护状态显示
- 运行模式切换
- 权限模式切换
- 自启动设置

**核心类**：
- `MainActivity` — 主界面

### 5. 消息总线 (MessageBus)

**职责**：模块间通信中枢

- 基于发布/订阅模式
- 异步事件分发
- 按事件类型订阅
- 异常隔离：单个订阅者异常不影响其他订阅者
- 队列溢出保护：队列满时丢弃最旧事件

**事件类型**：
```kotlin
enum class EventType {
    // 采集事件
    METRICS_SAMPLE, GPU_SPIKE_DETECTED, ENTITY_SURGE_DETECTED,
    
    // 决策事件
    SCENE_CHANGED, PROTECTION_TRIGGERED, PROTECTION_RELEASED,
    RISK_LEVEL_CHANGED,
    
    // 执行事件
    ACTION_EXECUTED, ACTION_FAILED, MODE_CHANGED,
    
    // 服务事件
    SERVICE_STARTED, SERVICE_STOPPED, HEARTBEAT,
    
    // UI事件
    UI_STATE_UPDATE, CONFIG_CHANGED,
}
```

## 进程设计

### 独立进程

守护服务 `GuardService` 运行在独立进程 `:guard` 中：

**优势**：
1. 游戏进程崩溃不会影响保护服务
2. 内存隔离，减少内存压力
3. 独立的生命周期管理

**通信方式**：
- UI 进程与守护进程通过 Service + Broadcast 通信
- 进程内部通过 MessageBus 通信

### 前台服务

守护服务以前台服务形式运行：
- 显示常驻通知
- 降低被系统杀死的概率
- 用户可随时从通知停止服务

## 配置设计

### 外置配置

所有可调参数全部外置在 `config/rules.json`：

```
config/
└── rules.json
    ├── general          # 通用设置
    ├── scenes           # 场景配置（可扩展）
    │   ├── gun_limit_challenge
    │   ├── thousand_star_domain
    │   └── new_nation_dungeon
    ├── gpu_monitor      # GPU监控参数
    ├── frame_monitor    # 帧率监控参数
    ├── risk_mitigation  # 风险缓释配置
    └── logging          # 日志配置
```

### 配置热更新

- 应用启动时从 assets 复制默认配置到内部存储
- 运行时从内部存储读取配置
- 修改配置后重启服务生效
- 后续游戏版本更新只需修改配置，不需更新程序

## 安全设计

### 红线原则
1. ❌ 禁止进程注入
2. ❌ 禁止 ptrace 调试
3. ❌ 禁止 HOOK
4. ❌ 禁止修改游戏 APK
5. ❌ 禁止绕过反作弊

### 权限最小化
- 只修改必要的系统频率参数
- 退出时恢复所有修改
- 不读取游戏内存
- 不修改游戏文件

### 数据安全
- 纯本地运行，无网络请求
- 日志不包含敏感信息
- 不收集用户数据

## 可扩展性

### 添加新场景
只需在 `rules.json` 中添加场景配置，无需修改代码。

### 添加新的执行器
实现 `ActionExecutor` 接口，例如：
- ADB 模式执行器
- 免 Root 模式执行器

### 添加新的采集器
继承 `BaseCollector`，例如：
- 网络延迟采集器
- 内存压力采集器
